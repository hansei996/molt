## 0. 为什么这一版不是「通用化」

`PLAN.md` §4.2 原定 v0.5 = **通用化（第二宿主适配器：MaiBot / 纯 Python 宿主）**。改判。

理由一：**第二宿主在真实环境里没有消费者。**

这个项目自己总结过一条教训，写在 [PLAN.md](PLAN.md) §5.2 里：概念正确不带来
star。`kabudu/permeant-os` 的描述和本项目几乎逐字同义（"Portable state
infrastructure for AI agents, enabling live migration across runtimes,
clouds, and hardware."），**0 star**。它缺的不是抽象层数，是一件别人能跑起来
的东西。再写一个没人用的 adapter，就是踩同一个坑。

理由二：**v1.0 的验收标准现在一条都没做。**

`PLAN.md` §4.3 写的是「v1.0 的证据 = 一条 `docker run` + 一条 `pip install`
命令」。而今天装一台壳要人肉干这些事：

1. 手写 `molt-agent.json` / `molt-homer.json`（十几个字段，其中一个写错就静默不动）
2. 从账本机器上 `cat warden.token`，再抄进另一台机器的 JSON
3. 猜壳名 —— 猜错的症状是「它永远不动」，而不是报错
4. 自己想办法把它放进启动项

这不是"还差一点"，这是**陌生人装不起来**。

理由三：**能证明「不只是给作者自己用」的东西，是可安装性，不是抽象层数。**

所以这一版做**可安装、可自检**；通用化推到 v0.6，而且届时要选一个有真实消费者
的第二壳 —— NAS 上那个容器壳（`homer` 这条路）本身就是第二个壳，可以先把它的
接口抽出来，而不是虚构一个 MaiBot。

## 1. 中心思想

> **生成器自己认为对，不算数。**

v0.4 学到的是「最贵的错误全都长得像成功」。这一版把它用在配置生成上：
`molt init` 写出来的每一份配置，落盘之前都**先交给守护进程自己的
`Settings.load()` 读一遍**。读不过就不写盘，并把加载器说的话原样打给人看。

同一个道理的第二面是 `molt doctor --config`：它能拿一份**真实的**配置，回答
「这份配置现在能用吗、不能用是卡在哪一步」。

## 2. 任务

| # | 任务 | 状态 | 验收标准 |
|---|---|---|---|
| T1 | `molt init` 生成三种角色的配置 | ✅ 完成 | `--role agent/homer/warden` 都能生成；生成物**过真加载器**才落盘；缺 `--shell` 明确拒绝而不是猜；不覆盖已有文件，`--force` 留 `.bak` |
| T2 | `molt doctor --config` 自检 | ✅ 完成 | 一份真配置能判三件事：加载器读得过吗 / 账本能连上吗 / token 对吗；401 与"连不上"分两种话 |
| T3 | 十分钟装一台壳的文档 | ✅ 完成（[INSTALL.md](INSTALL.md)，含 8 类常见症状对照表） | `docs/INSTALL.md` 从零到「它动了」的每一步都可复制粘贴；README 首屏两条命令 |
| T4 | 陌生人流程演练 | ✅ 完成（`tools/rehearse-install.py`，可重复跑） | 在一个**全新目录**里按 `INSTALL.md` 走一遍，记录每一处卡住的地方并修掉 |
| T5 | 版本 0.5.0 + 文档回写 + 提交 | ✅ 完成 | `molt --version` = 0.5.0；PLAN/ARCH/README 有这一版；`pytest` 全绿 |

### T1 的细节

`molt/initcfg.py`：

- `agent_template()` 的 `execute` **刻意是 `false`** —— 第一次装上只观察不动手。
  这个字段为真意味着「这台机器会自己关机」。
- `homer_template()` 的 `dashboard_host` **默认 `0.0.0.0`** —— 容器里监听回环等于
  没有监听（v0.3 真机踩过：容器里起了，宿主机映射出去的端口后面什么都没有）。
- `new_token()` 用 `secrets.token_urlsafe`：结果不含 `=` `+` `/`，塞进 JSON、
  URL、shell 变量都不会被转义咬到。
- 壳名**不猜**。账本里的 `target_shell` 是**别人写下的字符串**，猜错会让这台机器
  永远等不到自己的那一代，而且没有任何报错。

### T2 的细节

`doctor --config` 把三件事分开报，因为它们的修法完全不同：

| 现象 | 意思 | 怎么修 |
|---|---|---|
| 加载器读不过 | 这份配置守护进程自己都读不了 | 按它列出来的字段改，或者重跑 `molt init --force` |
| 连不上 | 账本没起来 / 地址错 / 被防火墙挡了 | `curl -sS -o /dev/null -w '%{http_code}' <url>/status` |
| HTTP 401 | 连上了，token 不对 | 从账本机器的 `<root>/warden.token` 抄 |

## 3. 真机演练（T4 的证据）

`tools/rehearse-install.py` 在一个**全新临时目录**里按 `INSTALL.md` 从零走一遍，
五步全部通过：

```
第 1 步：molt init --role warden          → token 已生成（32 字符），打印的 serve 命令带着它
第 2 步：起账本（127.0.0.1 随机端口）      → 账本在线
第 3 步：molt init --role agent           → execute 默认 false（只观察）
第 4 步：molt doctor --config             → 加载器读得过 + 连得上，token 也对
第 5 步：守护进程 --once                  → · execute 是 false（只观察，不动作）
                                            [idle] 账本里还没有任何一代快照
```

第 5 步那两行是这一版最关键的地方：它证明**一份由生成器写出来的配置，真的被
守护进程读进去了、真的连上了账本**。在这之前，这一步的失败方式是「它不动」，
没有任何输出可以据此排查。

这个脚本留在仓库里而不是一次性脚本，理由是：**"装得起来"是一个会退化的性质**，
它必须能被重跑。将来任何一次改动让 `molt init` 生成出一份读不过的配置，这个
脚本会立刻红。

## 4. 不在这一版做的（以及为什么）

- **通用化 / 第二宿主** —— 见 §0，推到 v0.6，且要有真实消费者。
- **让 `memory_companion` 的记忆变得可回忆** —— 那是改别人的插件行为，而且需要
  主人先决定「档案」还是「对话记忆」，不是技术问题。
- **把 `dsh-port.ps1` 接成"改完自动重载"** —— 已经做了自动纠偏（agent 每轮检查
  并重启壳），但"改完不重启"仍然不现实：`AstrBotConfig` 在内存里缓存，这属于
  AstrBot 的行为，不改它的核心。
- **断点续传** —— 归档约 4.5 MB，重传成本远低于维护续传状态。
