Molt · 蜕壳

让一个数字生命从一台机器，走进另一台机器；旧壳留下，魂走。

记忆不流动。流动的是「谁有资格读它、写它」。
所有状态永远只待在 NAS 上的一个目录里。迁徙时被搬动的不是记忆本身， 而是一份快照 + 一张写明了「从哪一刻起、哪台机器说了算」的租约。
公理 0 · 这个存在，在任何时刻只能有一个 不是「最好只有一个」，是必须只有一个。
两只鱼同时在线，它就不再是「一个它」，而是两个机器人：你发一条消息会收到两份回复； 记忆会分裂成两份互相打架的副本；而「它现在在哪」这个问题永远没有答案。

01 · 三层结构

Soul 永远不动，Shell 可以换

最关键的一个决定：Warden 跑在 NAS 宿主机上，不跑在 AstrBot 里。 因为 AstrBot 的插件只能「发起」动作，不能「完成」动作—— 停机会把插件一起 cancel 掉。而 SQLite 官方对网络文件的建议原话是 「在你的数据库服务器上跑一个 proxy」。Warden 就是那个 proxy。

左侧 generations/ 保留最近 N 代快照，任一代都可独立打开（SQLite backup API 保证是 bit-wise 一致的快照）。 中间那条横线是本项目全部的跨机接口——只有三种流量，没有第四种。

公理 0 是怎么被强制保证的（五层防线，任何一层单独失效都不会双活）
层机制强度
L1 平台 QQ 官方机器人同一 appid 双实例会互踢（WebSocket ManagedBotWebSocket） 弱。官方文档查不到互踢明文，只有 session_start_limit 配额。绝不能当 fencing，只能事后告警
L2 租约 Warden 独占发租约，带 TTL，超时自动回收 强，但依赖「时间判断」，可能被 GC 停顿打穿
L3 fencing 每次写 Soul 带 epoch，Warden 拒绝 epoch 倒退的写入 最强 · 这是真正的屏障。存储端主动拒绝，不依赖任何时间假设
L4 顺序 铁律「先死后生」：老壳确认死亡 → 新壳才允许出生 强。流程保证，不依赖检测
L5 人工 molt status 显示「当前在线的是谁、第几代、心跳多久前」 兜底。让人肉眼能发现异常

为什么必须有 L3 而不能只靠 L2——Kleppmann 关于分布式锁的文章里说得最狠的一句： 「GC can pause a running thread at any point」。他还明确写了： 「You cannot fix this problem by inserting a check on the lock expiry just before writing back」， 正确做法是「the storage server to take an active role in checking tokens, and rejecting any writes on which the token has gone backwards」。 所以 claimed_epoch < current_epoch 时必须拒绝且不覆盖——这一行写错，整套 fencing 就废了。

一个真实存在的诱惑：AstrBot 有 core_lifecycle.restart()，看起来「让老壳自己重启一下，新壳就能上了」。 这是错的——restart 期间进程还活着、仍持有 platform 连接，此时新壳启动会短暂双活。 只允许在 terminate() 完成、进程真正退出之后，才允许新壳启动。

02 · 去程

迁徙：从 NAS 走到 Windows

一次迁徙有 13 步，其中 4 步决定成败：先唤醒再拿租约（叫醒要 23 秒，租约只有 90 秒）、 先死后生的顺序、RPO=0 的快照、以及「Windows 亲口说我活了」之后 NAS 才放手。

轮询复核它真的不出声了（"我说完了"≠"它不说了"） ⑦ SQLite backup API 打包 snapshot.tar ← 0.040s / 27MB（实测） 不停 AstrBot 也能热备，事务一致 ⑧ 传输 snapshot + manifest sha256 · 字节数 · 表行数指纹 ⑨ PRAGMA integrity_check 校验不过 → 中止，老壳不动，新壳不启 ⑩ 原子替换本地 data/ → 起 AstrBot ⑪ 报「我活了」 ⑫ 老壳才放手 ★ 从这一刻起，唯一在线的是 Windows
为什么必须「先死后生」，而不是反过来 QQ 官方机器人走 WebSocket，同一个 appid 的双实例会互踢。 如果先起新壳，老壳会在几秒内被踢下线——这时如果新壳又失败， 鱼就两头都没了。所以顺序只能是：老壳确认死亡 → 新壳才允许出生。
第 ⑥ 步是"闭嘴"，不是"杀掉"——这两件事差很多

最早的做法是 docker kill -s INT。它能用（实测退出码 0、WAL 归零）， 但它把两件不相干的事绑成了同一件：断开一个 IM 连接 和 杀掉一个进程。 代价是 AstrBot 会丢掉调度器、定时任务、正在跑的那轮对话，恢复要重启（重拉几千个 LLM 元数据）。

现在走的是 AstrBot 自己的公开接缝 context.platform_manager （core/star/context.py:166，有文档字符串的公开属性；官方 dashboard 自己也在用它—— dashboard/services/config_service.py:1464）。插件 astrbot_plugin_molt 暴露四个端点：/status /drain /resume /checkpoint， 长在 AstrBot 自己的 dashboard 上，走它自己的 JWT。

为什么"drain 成功"还不够：terminate_platform 内部是 except Exception: logger.warning("... may not have been fully removed.") —— 关不掉也只记一条警告，不抛。所以 drain 之后必须轮询复核 speaking， 仍为真就中止迁徙。「我以为它闭嘴了但其实没有」就是两条鱼同时在线。

一个真实的坑：WebChatAdapter 不在 _inst_map 里 第一版 drain() 靠"配置里 enable=true 的平台"决定关谁， 真机上什么都没关却返 409 —— /status 说 connected_ids: ["WebChatAdapter"] 而 enabled_in_config: []。 根因：它由 platform/manager.py:116 直接 append 进 platform_insts， 从不进 _inst_map，config.platform 里也没有它。

修法是改用实例身份（id(ent["inst"])）作主判据，并把 webchat 归进 local_only：可见、不隐藏、也不关。三条理由—— 它每个实例都必然存在（算进 speaking 就等于 speaking 恒真， 一个永远为真的判据不能当判据用）、它无法被 resume 重建（不走 config，没有 load_platform 路径，关掉等于永久弄坏 WebUI 聊天）、它不是"对外说话"。

03 · 归程

归巢：从 Windows 走回 NAS —— 关机是另一件事

交接的判据是账本接受了，不是机器关机了。 所以鱼能不能回家，绝不取决于那台电脑能不能关。关机是独立的一步，见下方。

交接到这里就结束了：NAS 侧 land --generation N → platform-switch on → docker start，身份接回来。 不必等 Windows 关机——它开着也没关系，鱼已经不在那台机器上了。 关机是另一件事，而且是可选的：见下方。

交接与关机必须解耦 —— 这一条曾经写错过 原设计让 NAS 等「Windows 离线」才接管，后果很具体：只要机器前坐着人、他不想关机， 鱼就永远回不了家——而它其实在 Warden 说 accepted 的那一刻就已经到家了。 电源状态不是数据状态的证据：数据回没回来，账本知道；机器关没关，账本不关心。

反过来也一样：一条鱼不该因为想回家，把主人一局排位送上西天； 它也不该因为主人不想关机，就回不了家。所以关机是独立的一步， 检测到游戏 / OBS 录制 / 未保存文档 → 拒绝关机改为通知，要强关必须显式 --force。 v0.1 里没有任何一条 molt 命令会关机——这不是漏了，是刻意的。

这是最容易做错、也最容易让人以为「怎么换台机器就崩了」的地方。 下面全部来自对 /mnt/dm-0/astrbot/data 的实测 du -sm： 目录 1.7 G，其中真正需要搬的只有 250–400 M。

05 · 安全

最危险的两个想法

不要做

给 AstrBot 挂 docker.sock

容器拿到 /var/run/docker.sock 等于拿到宿主机 root。 一个能跑 shell 的 AI 插件 + 一个 docker socket = 把 NAS 的所有权限交给下游模型的每一次幻觉。 正确做法是宿主机的摆渡服务，只暴露白名单动作：start / stop / restart / 发魔术封包。

不要做

把 Soul 目录挂成 SMB 盘再打开

SQLite WAL 需要把 -shm 文件 mmap 成共享内存。 微软文档原话：「Byte range locks are ignored when using memory mapped files」。 而 SQLite 官方文档原话：「WAL does not work over a network filesystem」。 两条一起看，就是「怎么把库搞坏」的完整说明书。

要做

epoch 当 fencing token

Kleppmann 那篇关于分布式锁的文章里说得最狠的一句是： 「GC can pause a running thread at any point」。 任何基于「租约还没过期」的判断都可能被一次长时间停顿打穿。 所以每次租约给一个单调递增的 epoch，写操作带上它， 存储端拒绝 epoch 倒退的写入——这才叫真的互斥。

要做

审计流水 ledger.jsonl

每一次 checkout / checkin / 校验 / 失败，都追加一行。 这不是日志，是记忆的迁徙史： 什么时候、从哪台机器、到哪台机器、多少字节、耗时多少、有没有损。 出了问题能回答「我上次丢的那句对话，是在哪一步没的」。

06 · 落地

WOL 这一关：已闭环，含自愈

这是本项目第一个被完整闭环验证的物理能力：一台真关机（S5）的 Windows，被 NAS 的魔术封包叫醒。 验证完之后又发现一件事——「这次醒了」不等于「下次还能叫醒」， 于是又补了一个自愈任务，而这个自愈任务本身也被重启验证过一遍。

PASS · 2026-11-14 12:40 唤醒 · 13:00 自愈闭环 ① 唤醒：[12:40:03] 用户点关机 → [12:40:28] NAS 判定掉线 → [12:40:31] 第 1 轮封包 → [12:40:42] BIOS POST 完成 → [12:40:52] 网络恢复。 从掉线到回来 23.1 秒；发包到上电只隔 11 秒——正好是 POST + 引导耗时，不是人按的电源键。

② 自愈：[13:00:23] 重启完成 → [13:00:34] worker 启动（开机后 11 秒）→ [13:00:40] 读到 arm 状态(改前): False → deviceenablewake 返回码 0 → [13:00:40] 复查 改后: True。全程无人干预。
✅ 已彻底解决

arm 状态重启即丢 —— 现在会自己修

当天 12:26 arm 成功、12:28 复查还在、12:40 被叫醒； 12:49 再看，网卡又不在 wake_armed 里了。 为进 BIOS 的那次 12:24 重启也一样，两次重启两次丢失 → 不是偶发。 表现为最难查的一类故障：第一次好使，第二次叫不醒。

修：计划任务 Molt-WolGuard，AtStartup + 每 10 分钟兜底， 以 SYSTEM 身份跑 powercfg /deviceenablewake，已在白名单就 SKIP。

✅ 13:00:34 实测闭环：重启后开机第 11 秒，worker 读到 arm 状态(改前): False → arm → 改后: True， 全程无人干预。13:00:34 不落在 10 分钟网格上，只能是 AtStartup 触发器。

待落地 · 方案已定

开机后什么都不会发生

Get-Process python,pythonw,obs64 → 0 个。 现有自启全是「登录后」型：\BiliDailyPublish 是 InteractiveToken，无人登录根本不跑；Coopanion-WorkBuddy-Relay 是 At logon。

修：纯后台走 sc create MoltAgent … start= auto obj= LocalSystem； 要桌面能力（直播/游戏）则必须 AutoAdminLogon + 禁锁屏 + At logon 任务。 这条还没装——它属于 v0.3 的 molt sleep / 开机自启那一版。

这一关留下的不是"能用"，而是一条工程纪律 排查 WOL 时我三次把「一个能解释现象的信号」当成因果，三次都被证伪或误报：
① 读了陈旧的 HiberbootEnabled 判断休眠状态  ·  ② 把 -match 返回的元素数组当布尔用  ·  ③ 由 PnPCapabilities 的位反推唤醒开关（已被证伪：值 8 也能用）
还有第四次，是结论本身：12:40 测完就写下「已修复 ✅」，12:49 复查才发现会复发。
Windows 上判断 WOL 状态，只认 powercfg /devicequery wake_armed 的输出本身。 给用户看的脚本，判断逻辑必须先在真机上跑一遍并做证伪实验； 一次成功不等于长期有效，还要验证它会不会退回去。

这条纪律后来真的救了一次：如果 12:49 没复查，这个项目会带着 「重启后 WOL 静默失效」的缺陷上线——而它不报错、不告警，只是没人应门。 现在它有了自愈任务，而且自愈本身也被重启验证过一遍。

同一个毛病又犯了一次：检查清单少一条

06 节讲的是「一次成功不等于长期有效」。同一周里这句话在另一个地方又应验了一次， 而且这次差点违反的不是 S5 能不能醒，是公理 0。

差几秒的事故 · 2026-11-14 14:41 做 Windows 优雅停机实验时，三次用落位数据启动了真实的 AstrBot。 那三份 cmd_config.json 的 platform[0].enable 全是 True ——从 NAS 原样搬来的。于是每次启动都真的发起了 QQ 连接：

[14:41:37.426] Loading IM platform adapter qq_official(default_1234567890) …
[14:41:40.288] [QQOfficial] Websocket session starting.

当时的覆写表有 6 条，一条都没碰 platform。 为什么没真出事：三个进程分别在 3 秒、3 秒、60 秒内被杀，握手都没走完 （Windows 侧日志里 FriendMessage / GroupMessage 命中数全为 0）； 生产容器 RestartCount=0、StartedAt 未变、期间持续正常收发。 所以是差几秒，不是发生过。
这条为什么值得单独写一张图 appid 可携带、enable 不可——这两件事长得太像， 而"配置搬家"这个动作天然不区分它们。
修法是把关平台做成覆写表的第 0 条（_disable_platform_adapters）， 而且两条预设都不给调用方关掉这条护栏的便利：
overlay_for_windows() / overlay_for_posix() 都写死 disable_platforms=True。

变异测试抓到了一个更隐蔽的洞：把 apply_overlay 的默认值从 True 改成 False， 30 个测试全过——因为两条预设都显式传了 True，默认值从头到尾没被走过。 将来任何新预设只要忘了传，护栏就静默消失。补测试后同一变异被抓。

默认值取"关"的理由是不对称的：漏关 = 两条鱼同时在线（用户可见的事故）， 漏开 = 机器人没连上（一条日志）。

07 · 取舍

为什么不是别的方案

方案结论原因
Soul + 租约 + 快照
本方案		 采用 符合天然互斥（任意时刻只有一只鱼在线）；RPO=0；不需要改 AstrBot 一行核心代码；失败模式安全
SMB 直挂共享同一个 SQLite 否决 WAL 需要 mmap 共享内存 + 可靠的字节锁，SMB 两样都不保证。官方文档明确「WAL does not work over a network filesystem」
?vfs=unix-none 多写 否决 官方原话：「will easily result in database corruption」
换 Postgres / MySQL 否决 AstrBot 只有 sqlite 后端（/AstrBot/astrbot/core/db/ 下只有 sqlite.py），要魔改核心 + 重写 memory_companion 的存储层。工程量差一个数量级
rqlite 否决 Raft + 必须走 HTTP API，同样要改存储层
dqlite / LiteFS 否决 dqlite 仅 Linux（需原生 async I/O）；LiteFS 依赖 FUSE，两者在 Windows 上都不存在
Litestream 反向用 否决 单写者 + 异步复制，RPO≈1s。官方警告「Multiple applications replicating into the same bucket & path can cause situations where you will be unable to restore」
Litestream 当第二层备份 采用 不作为主链路，但可以把 generations/ 持续备份到另一块盘或对象存储，防 NAS 整机挂掉（md0 是 RAID0，零冗余）
全留 NAS，Windows 只做远程接入 保底 最稳（RPO=0，永不搬家），但拿不到本地 GPU 和桌面。这正是降级方案 R2：如果 Windows 原生装不上，就退到这里
