# 等你拍板的、已定案的、等时机的

这份文件只有一个用途：**把"需要老大拍板"的东西集中到一处**，别再散在四份 PLAN 里。

规则很简单：

- 能我自己决定的，不进这张表 —— 我做完了写进 `docs/ARCH.md`，并在那里标明"可被推翻"。
- 进这张表的，**没拍板之前就按下表最右一列那样跑**。也就是说：不拍板不会让系统出
  问题，只会让某个功能一直停在半路。

## 一、等你拍板

### D1. `schedule` 触发源的两个产品决定

判据（到点了吗）已经写好了：`plugin/command.py` 的 `schedule_spec` / `schedule_problem` /
`schedule_due`，纯函数、跨午夜正确、判不了返回 `None` 而不是 `False`。缺的是外面两件事：

| 编号 | 问题 | 候选 | 现在的默认 |
|---|---|---|---|
| D1a | **谁来敲这一下？** | ①插件里的定时任务 ②`molt-agent` 每轮顺手看一眼 ③账本侧 | 都不敲 —— `schedule` 不会自己触发任何东西 |
| D1b | **敲完怎么让人看到？** | ①只写日志 ②允许它主动发一条不是回复任何人的消息 | 只写日志（所以半夜三点的提议等于什么都没发生） |

**D1b 的张力**：我们刚定过"落地播报只挂在主人说的话上"（`docs/V0.6-PLAN.md` §2.1）。让
它主动发一条定时提议，是那个边界的例外 —— 值得，但必须明说。

**为什么不拍也能跑**：`schedule` 目前只是一个"配置了也不会触发"的诚实空壳；配了坏值
会被 `move_policy_refusals` 拦住并说"读不懂"，不会静默失效。

**说全一点（2026-11-15 审计）**：`schedule_due()` 这个"到点了吗"的纯函数**全仓库没有任何
调用方** —— 只有测试在调它。这是 D1a 没拍板的直接后果，不是漏写：谁去敲这一下没定，
就没有人该调用它。看到"判据已写好"时，请一起看到"但没有人问它"。

### D1.5 落位回 NAS 时，要不要也换掉 `dashboard.jwt_secret`？

审计（`docs/AUDIT.md` 第 6 条）发现文档说"换密钥是默认行为"，而代码里只有 Windows 路径换：

| 落位方向 | `rotate_jwt` | 位置 |
|---|---|---|
| 落在 Windows 壳上 | **`True`（每次换）** | `molt/overlay.py:336`（`overlay_for_windows`） |
| 落回 NAS 容器 | **`False`（不换，沿用上一台壳的密钥）** | `molt/cli.py:1723`（`cmd_land` 非 Windows 分支） |

**代价对比**：换 → 那边 dashboard 上已登录的会话失效一次（要重新登录）；不换 → 从 Windows
搬回来的快照里带着 Windows 的密钥，于是"攻破 Windows 等于攻破 NAS"这条**在回家方向上仍然成立**。

**现在的默认**：不动（`False`），因为改它会让一个已登录的 dashboard 在鱼回家那一刻掉线。
**我的建议**：两侧都换，接受一次重新登录 —— 但这条会影响你正在用的界面，所以等你点头。


### D2. L3 壳属性表 —— **已定案并落地（2026-11-15）**

账本里每一代原本只记了"哪台壳"，没记"那台壳是什么"。现在它记了：

| 字段 | 状态 | 落在哪里 |
|---|---|---|
| `role`（`nas`/`desktop`/`cloud`/`unknown`） | ✅ 已做，**显示给人判断**（代码里没有一条 `if` 因它改变行为） | 账本 `shells`、`GET /shells`、`POST /shell`、`molt declare`、`molt shells`、`/where` 的「是什么」列、`/molt where` 每行 |
| `wakeable`（能不能被 WOL 叫醒） | ✅ 已做，**真的拦住魔术封包** | 同上；另外 `molt migrate` 发封包前会查它（2026-11-15 补的，见下） |
| `gpu`（型号，空串=确认没有） | 🟡 能填，**不参与任何判断** | 只显示 |
| `cost_per_hour` | 🟡 能填，**不参与任何判断** | 只显示 |
| `label` | 🟡 能填 | 只显示 |

**`role` 的"参与"要说准**：它参与的是**人的**判断（人看着"/where 说这是 nas"决定搬不搬），
不是代码里的 if。代码目前没有一条分支因为 `role` 改变行为 —— 不想让它替人决定"NAS 该不该醒着"。

**`wakeable` 的"参与"是硬的**（2026-11-15 补）：`false` → `molt migrate` **不发**魔术封包，
并说清"这台要人手动开"；`None`（没声明）→ 老行为，给了 `--wake-mac` 就发。
把 `None` 当 `false` 会让一台没登记的机器永远收不到封包，症状看起来却是"叫不醒"。
写进账本的方式：`molt declare --shell X --wakeable` / `--no-wakeable`（后者是 1.2.1 补的，
在此之前"叫不醒"这个状态在 CLI 上表达不出来），`molt shells` 分别印「可唤醒」/「不可唤醒」/ 什么都不印。

**没登记就少一段，不编。** `unknown` 只在**人明确填了 `unknown`** 时出现 ——
"我不知道"不会被伪装成"我确认过它不是 NAS"。同一条规矩对内层字段也成立：
只声明了 `role` 的壳，它的 `wakeable` 是 `None`（没说过），**不是 `False`（说过不能）**。
上一版这里写的是 `bool(attrs.get("wakeable", False))` —— 两个不同的意思被压成同一个值，
于是按它判断就会**不发**封包，而看起来像"账本说它不用叫醒"。

**为什么 `gpu`/`cost_per_hour` 先不参与判断**：判断要花钱（错误判断的代价是不该搬的时候
搬了）。现在只有两台壳、且人就在旁边，没有排序需求；等真的有三台以上、或者要按成本
选机器时再让它们参与。那时候要动的是 `move_policy_refusals()` 与提议文案 ——
**加一个字段进判断，比加一个字段进存储危险得多。**

### D3. 措辞：账本记的是「第几份快照」，不是「第几条命」—— **已定案（2026-11-15，主人）**

主人的原话：

所以定下这条（实现见 `molt/language.py`、`docs/ARCH.md` §14.11）：

| 场景 | 说法 |
|---|---|
| 它自己说 / 自己记 | 不提数字：「（我刚从 UGREEN-776B 那边过来 —— 中间睡了一觉。）」 |
| 人看的页面与命令行 | 「第 N 次搬家」/「快照 #N」 |
| 协议字段 | 不动：`generation`、`--generation N` |

**为什么记在这里**：这不是文案偏好，它决定"下一个改这块代码的人会不会把数字又塞回
播报里"。钉住它的是 `molt/tests/test_language.py`：「输出里不许出现那个字，播报里
连数字都不许有」。

### D4. 插件配置同步的范围 —— **已定案（2026-11-15，主人）**

主人的原话：

> 「做下一个更加有用的功能，就是多端的插件配置同步，注意，如果有相同插件才同步，
> 如果某个插件只有某一段独有，就不能同步。」

已按这个形状实现（`molt/pluginsync.py`、`docs/ARCH.md` §14.12）：只同步两边都装了的
插件的配置；只有一边装了的插件，**两边都不动**（不装代码、不写配置、不删配置）。
默认空跑，`--apply` 才写，旧文件留备份。

**两个我自己做的、可以推翻的默认**：

1. **结构看起来不一样就跳过**（顶层键交集 < 20%）。真实数据里
   `astrbot_plugin_private_companion` 是 15 键 vs 1008 键的两种版本，覆盖过去不会报错，
   只会把对方不认识的键塞进去。要覆盖得显式 `--force`。
2. **每个壳只保留最新一份配置包**（不像快照那样留历史）。配置是"现在的偏好"，
   不是"发生过的事"。


D4 的补充（2026-11-15）：**页面上那个同步按钮只写这台机器**。它读的是对面发布的包、写的是本机的 `data/config/`；对面要改，去对面点。

「每个壳只保留最新一份」这条原来**没有测试钉着**（审计第 22 条），2026-11-15 补了
`test_pluginsync.py::test_publishing_twice_keeps_only_the_newest_bundle` —— 原来它靠的是
"文件名恰好没加时间戳"，谁哪天改成备份式命名，文档就会静默变成谎话。

### D5. 写完插件配置，要不要在页面上加一个「重载这些插件」按钮？

`molt sync-plugins --apply` 只写文件；插件手里还是旧配置（`AstrBotConfig` 是**插件载入时**
从磁盘读的，`astrbot/core/star/star_manager.py:1167`）。所以"写完 → 让它生效"还差一步重载。

| 编号 | 候选 | 现在的默认 |
|---|---|---|
| D5 | ①一直手动（`tools/reload-plugin.py`）②写完弹一句「要现在重载吗？」+ 按钮 ③写完自动重载 | **①手动**；页面脚注写明差这一步 |

**为什么不自己拍**：重载是 `Terminating plugin … → Loading plugin …`，会把插件正在做的事
打断（`memory_companion` 的记忆整理、`workbuddy` 的轮询都会重新开始）。同步本身是低频动作，
"多敲一条命令"成本很低；而"替人决定现在打断哪个插件"的代价不低。

**我的建议**：②——把"要不要现在重载"交给在场的人，而不是替他决定。

**为什么不拍也能跑**：不重载只是"配置没生效"，不会坏；`tools/reload-plugin.py` 随时能补这一下
（自签 JWT 调 `POST /api/plugin/reload`，只会重载指定插件，整机不掉线）。

### D6 要不要把插件**代码**也一起同步（等老大拍板）

**现在的默认：不碰插件代码。** 只做版本检测：同步时把两边的版本念出来，
让人决定升级哪一台。

| 候选 | 好处 | 代价 |
|---|---|---|
| ① 从不碰代码（默认） | 每台壳自己决定装什么；不会有半截升级 | 版本漂移得靠人看见 |
| ② 只同步两边都装了的插件的代码，带确认 | 一只鱼换壳后能力一致 | 覆盖别人机器上的插件目录；升级失败会留下半坏状态 |
| ③ 升到某个"期望版本"，不自动装 | 兼顾一致与可控 | 要有版本清单与来源（市场？git？） |

真机背景：`astrbot_plugin_private_companion` 在 NAS 是 7.1.18、Windows 是 6.5.6，
配置顶层键 1008 vs 15；7.x 的 `plugin_data` 里还有一条 Windows 绝对路径
（`.storage-backend-state.json` 的 `sqlite_path`）。**这两台机器上的"同一只鱼"
目前能力集不同**，而迁移不会告诉你这件事 —— 现在会了。

## D8 · 搬家时自动把插件配置写回目标壳（已定案，2026-11-15，主人）

**定案：默认自动，不需要人再点一次同步。** 规则见 `docs/ARCH.md` §14.16 与 `molt/landcfg.py`。

| 项 | 现在 |

## D9 · 指向本机服务的 provider，搬家时删还是留（已定案，2026-11-15，主人：「这个帮同步 workbuddy/deepseek-v4.1-flash 吧，这个应该可以同步」）

| 情形 | 默认动作 | 怎么改 |
|---|---|---|
| `api_base` 是回环地址（`127.0.0.1` / `localhost`） | **删**（source + 引用它的 provider 一起删） | 那台机器上确实有那个服务时，`molt land --keep-provider-source <id>` 或 agent 配置 `keep_provider_sources: [<id>]` |

| 想连"本机没有这个服务"也保留 | 用 `--keep-provider-source` 点名即可（代码不判断服务是否真的在听） | 后果自负：AstrBot 启动日志会多一条 WARN |

为什么默认是删：**猜错的方向不对称**。多留一条死配置只是日志里多一行；默认保留会让每一台
没装那个插件的机器都背上一条指向空气的 provider，而这类"看起来配好了"的配置最难查。

配套（同一批改的、不需要单独拍板的）：`plugin_data/astrbot_plugin_workbuddy` 进搬家名单
—— 16 KB 的登录凭据和调度状态，没有它，点名保留的 provider 能加载但用不了。

### D10 · 搬家前必须先确认目标壳活着（已定案，2026-11-15，主人）

**规矩**：先确认目标开机 → 关着就先叫醒 → **叫不醒就不搬**（源壳继续说话，鱼不死）。

| 项 | 取值 | 理由 |
|---|---|---|
| 活着的判据 | 账本心跳 **≤ 25 秒**，且 15 秒观察窗口里**亲眼看到它又跳了一拍** | 刚开机没人登录的机器 ping 得通、但没人接快照；只看"最后一拍不算久"会在关机瞬间误判 |
| 免发封包 | 只有心跳 ≤ 10 秒才免；否则即使"看着活着"也照发 | 封包幂等，多发一封没有代价；少发一封就是四分钟静默（23:38 那次） |
| 叫醒的凭据 | 账本里的 `wake_mac`（壳属性） | MAC 是机器的属性，不该活在某个脚本的配置里 |
| 等它报到 | 默认 180 秒，`--wake-timeout` 可调 | 真机实测 23.1 秒上电，留足余量 |
| 失败时 | 退出码 5，**不 drain、不交接** | 「鱼没死」比「这次搬成功」重要 |
| 逃生口 | `--skip-target-check` | 只给测试和明确知道自己在干什么的人 |

**没有替你决定的一件事**：关机票没有有效期。今天 23:04 那次关机，就是一张更早写下的票
在执行。要不要给它加 TTL、或只允许"刚交接完 N 分钟内"生效 —— 这会影响"我明天早上想让它回家
并关机"这种用法，所以留给你拍板。

### D11 · 交接完成的定义（已定案，2026-11-15，主人）

**判据**：源壳交出去之后，必须在 `--confirm-timeout`（默认 180 秒）内
看到账本写下 `consumed_by == 目标壳`；否则**整件事按失败处理**：

1. 抢回租约（新 epoch，挡住宿位）
2. resume 源壳的平台适配器
3. 退出码 6

**为什么不是"再等一会儿"**：等待不会让另一边突然长出能力；而源壳哑着的时候，
人发消息没人回 —— 那种"看起来像死"的状态每多一秒都在消耗信任。

**没有替你决定的**：`--confirm-timeout` 的默认值（180 秒）。它取决于那台
目标机器开机 + 落位要多久；真机实测冷启动落位约 190–240 秒，所以 180 秒
偏紧 —— 但调大它就意味着"哑着更久"。你说了算。

#### M2 + 链式收尾：搬完再把旧壳关掉（2026-11-17 主人追加）

主人的原话：「早上 9 点定时搬到 NAS，同时把 Windows 那台关掉」，
以及补充的边界：「如果早上 9 点，鱼还在 Windows，那就搬回 NAS 并把 Windows 关机；
如果鱼就在 NAS，那就不动」。

**这条完全是 M2 的一种策略，不是新机制。** 一条策略就够了：

```bash
molt policy set --id morning-home \
  --source desktop-h2kgiao --target ugreen-776b-8b7896df \
  --at 09:00 --window-minutes 30 --daily-limit 1 --power-off
```

- `--source` 必须是**执行搬家命令的那台壳**（Windows）—— 搬家是"这边 drain、打包、推走"。
- 「鱼已经在 NAS 就不动」是**结构性保证**，不是又写了一条 if：守护进程只在
  `latest_generation.consumed_by == 自己的壳` 时才会自动搬；鱼在 NAS 时，
  Windows 这边既不满足这条，AstrBot 也没在跑，两条闸都会让它什么都不做。
- 关机**走已有的关机票**（`POST /power` → 那台壳自己的 leave 分支执行），
  没有新开旁路；`/molt shutdown`、`/molt keep` 与它共用同一张票。

**顺序（写死在代码里，不能只写在文档里）**：

| 步骤 | 判据 | 不成立时 |
| --- | --- | --- |
| ① 目标已经就绪 | 心跳 ≤25 秒且观察窗口里又跳一拍（否则先叫醒并等它报到） | 不搬，鱼留在源壳 |
| ② 交出去 | `migrate` 等到账本写下 `consumed_by == 目标壳` | 抢回租约 + `resume`，鱼回源壳，**不放票** |
| ③ 播报送达 | 新壳往账本写 `arrivals[<快照>].delivered == true`，且回执是这一代、是新壳写的 | 等 `arrival_timeout_seconds`（默认 120）后**不关**，只记 `skipped` |
| ④ 关旧壳 | 前三条都成立才 `POST /power` 放票 | — |

**失败时鱼在哪、Windows 会不会被误关**：

| 情况 | 鱼在哪 | Windows |
| --- | --- | --- |
| 叫不醒 / 没接走 | 留在 Windows（回滚已把平台恢复） | **不关**（一张票都没放） |
| 搬家进程失败（退出码非 0） | 留在 Windows | **不关** |
| 接走了、但播报没送到人眼前 | 在 NAS | **不关**（等不到回执，只记 `skipped`） |
| 全部成立 | 在 NAS | 放票 → 由 Windows 自己的 leave 分支执行关机 |

> 「旧壳」如果恰好是账本所在的机器（homer 自己），账本的 `power_verdict()` 会
> **refuse**：关掉账本 = 整个 molt 停摆。所以那张票会被如实拒绝，而不是误关。

**还没做**：真机整链（9 点自动搬 + 关机）没有跑过 —— 需要主人点头，且不能在

#### 2. M2：定时自动（**免确认**）

**长什么样**（写进账本的许可对象，示意，字段名未定）：

```json
{
  "id": "nightly-home",
  "mode": "schedule",
  "target": "ugreen-776b-8b7896df",
  "cron": "0 3 * * *",
  "window_minutes": 30,
  "max_per_day": 1,
  "granted_by": "hansei",
  "granted_at": "2026-11-16T01:00:00Z",
  "expires_at": "2026-12-16T01:00:00Z",
  "on_failure": "report_on_next_turn"
}
```

**凭什么可以免确认** —— 四条，缺一条都不行：

1. **授权发生在人还在场的时候。** 写这张许可的那一刻，人是清醒的、知道自己在允许什么；
   半夜三点那条路只是执行，不再新增决定。
2. **范围是封闭的。** 目标壳写死、时间窗写死、每日次数上限写死、过期时间写死。
   没有"任意时间搬去任意地方"这种许可。
3. **可撤销，且立刻生效。** 许可存在**账本**里（权威），不是存在那台壳的配置里；
   每轮 tick 都重读。`molt policy off <id>` 一次调用即失效 —— 不需要等那台壳重启。
4. **失败不吞。** 每次尝试在账本里留一条 `attempt`（时间、目标、结果、原因）；
   失败**不重试**（下一次到点再说），并且在**下一次和人说话时**主动交代一句。

**执行顺序（和 M0 完全同一条路径，只是把两次确认换成四条前置条件）**

```
1. 读许可 + 读账本（无租约？目标是不是我？源壳安静吗？今天搬过了吗？）
2. 目标不在线 → 发封包（由账本发）→ 等心跳（默认 180 秒）
3. 等不到心跳 → 失败：什么都不做，鱼留在源壳；账本记 attempt
4. 等到心跳 → 再过一遍第 1 步（窗口可能已经过期、别人可能抢了租约）
5. drain → 快照 → 打包 → 上传 → 交还租约
6. 在 --confirm-timeout 内没看到 consumed_by → 抢回租约 + resume + 退出码 6
```

**失败时鱼在哪**：永远在**源壳**。第 1–3 步失败连 drain 都不会发生
（`_wait_for_target_heartbeat` 在 drain 之前）；第 6 步失败会 resume。
**没有任何一步是"先把鱼弄哑再想办法"**。

**静默失败怎么报**（三处，按"人会不会看见"排序）：

| 通道 | 内容 | 人要不要主动看 |
|---|---|---|
| 账本 `attempts[]` | 每次尝试一条：成功/失败/原因/耗时 | 要（`molt status` / `/where`） |
| `/where` 页面 | 最近一条 attempt 的结论，失败标红 | 打开页面就看得到 |
| **下一次对话** | 它开口第一句带一句「昨晚 3 点那次没搬成，因为：目标叫不醒」 | 不用，聊天时自然出现 |

**明确不做的**：不新增"它自己在半夜发一条 QQ"的通道。2026-11-15 我们删掉过
`molt announce`，当时的判决是「**用一条假消息换一条真记忆**」不划算；
半夜主动发消息会破同一个例。要不要破，是下面选项 C 的一部分，**你说了算**。

**撤销与"手滑"防护**：

- `molt policy list` / `off <id>` / `test <id> --dry-run`（只算不搬）
- 连续失败 2 次 → **自动暂停这张许可**并记一条 WARN（防止"每天半夜都失败"没人发现）
- 许可到期自动失效；不续期就是不续期

#### 3. M3：条件自动（可选，**免确认**）

**触发源是条件谓词，不是任意脚本。** 只允许一份**封死的清单**（新增一条要改代码 + 发版）：

| 谓词 | 判据 | 判不了时 |
|---|---|---|
| `source_idle` | 源壳最近 N 分钟没有对话 | **拒绝搬**（未知 ≠ 空闲） |
| `target_idle` | 目标壳最近 N 分钟没有对话 | 拒绝搬 |
| `off_hours` | 本机时间在 `[start, end)` 内 | 拒绝搬 |
| `on_ac_power` | 目标/源壳接着电源 | 拒绝搬 |
| `gpu_idle` | 目标壳 GPU 利用率 < X%（需要那边装传感器） | 拒绝搬 |

规矩和 `schedule_due()` 一致：**判不了就返回 `None`，不是 `False`**，
而 `None` 在闸门里一律等于"不许搬"。

#### E4 的后半段：守卫要不要顺手把它拉起来（**等你拍**，2026-11-18）

先摆事实：2026-11-18 03:00 那次真机补验测到 —— **agent 被杀掉之后，用 Startup 的
`molt-agent.vbs` 拉起，3 秒内 `/health` 就回来了**（`6191` 三个方法齐全）。也就是说
"拉起来"这个动作本身是**便宜且已知可行**的，问题不在技术上，而在该不该让它自动做。

两个选项，各自把代价写清楚：

| | 做法 | 好处 | 代价 / 风险 |
|---|---|---|---|
| **A** | 守卫判定 `dead` 后**自动执行一次** `wscript.exe …\molt-agent.vbs`，然后立刻补一条 `agent-restarted` 告警 | 09:00 那条策略不再依赖"人刚好看见告警"；E4 从"能报警"变成"能自愈" | 判据错了会**反复拉起**（比如状态文件写不进去 → 每 300 秒拉一次）；拉起前必须查"是不是已经有一个在启动中"（`BOOT_COOLDOWN_SECONDS=180` 已经在 agent 内部挡重复拉起，但守卫这一层没有）；如果 agent 是因为**配置坏了**起不来，A 会变成"每 5 分钟失败一次"的噪音源 |
| **B** | 只告警，人看到再手动拉起（**现状**） | 任何时候出问题，机器状态都是"人最后决定过的样子"；不会有自动重启风暴 | 夜里 agent 死了、你早上 9 点才发现——策略空转一次；红条会挂到有人看见为止 |

**我推荐 A，但带三条硬约束**（写在这里，选了 A 才实现）：

1. **只拉一次，不拉第二次**：同一个 `dead` 事件只尝试一次；失败就转成告警，
   等下一次"人工确认"（比如人回一条 `/molt status`）才重置计数 —— 不做无限重试。
2. **拉起之前先确认"没有在启动中"**：查进程 + 查 `last_boot_at` 的 180 秒冷却，
   和 agent 自己的 `BOOT_COOLDOWN_SECONDS` 用同一个常量，不另写一套。
3. **拉起这个动作必须留痕**：账本里写 `agent-restarted`（含它从哪一刻开始哑、
   被判成 `dead` 的理由），否则"它自己好了"会变成新的不可解释现象。

为什么不是 B：你已经在 NAS 常驻、Windows 当工具的用法上了 —— 若 agent 死了没人拉，
丢的不只是"一次搬家"，是**这台机器上还能不能遥控**（`/molt machine on/off`、
DSH 代转全都要经过 agent）。A 的风险是"多拉几次"，B 的风险是"整夜不可达"。
两者都不是零，但在这个场景里前者可恢复、后者不可恢复。

## D16 · 「遥控优先、搬家兜底」与 09:00 那条策略（结论，只写判断不写代码 · 2026-11-17）

主人问了两件事：这套「遥控优先、搬家兜底」跟 M2 定时搬家冲不冲突；那条
`morning-home`（09:00 搬回 NAS + 搬完关 Windows）该改成「不搬、只关机」还是留着。
下面是我的判断，**没有改任何代码**。

### 一、先说清：遥控的是「工作台」，搬家的是「本体」

- DSH 是 web 服务 —— 下指令、看它干活、看屏幕，走 HTTP 就够了，**不必把鱼搬过去**。
  这一层「遥控优先」我完全同意。
- 但 AstrBot 是**本体**：它得有一台常开的机器连着 QQ，才谈得上"在"。所以
  「搬到哪台」回答的不是「能不能被找到」，而是**本体托管在哪台**（省电、噪声、有没有显卡）。
- 于是结论是：**不冲突**，因为两句话在回答不同的问题 ——
  「遥控」回答"人怎么够得着它"，「搬家」回答"它自己住在哪台机器上"。

### 二、冲突只在一种读法下才会出现

如果把「遥控优先」读成"本体可以不存在于任何固定机器"，那定时搬家确实多余。
但公理 0 要求同一时刻只有一只鱼在线 —— **本体必须有一个家**。所以真问题不是
"要不要搬"，而是「默认的家在哪，什么时候允许它离开」。

### 三、你列的三种真实搬家场景，归一下类

| 场景 | 搬家能解决吗 | 遥控能替代吗 | 结论 |
|---|---|---|---|
| 目标机要关机 / 休眠 | ✅ 把本体移走再关 | ❌ 机器关了就没什么可遥控 | **必须搬**（可以定时） |
| 端口或网络断了、没人能开 | ✅ 换一台能连的壳 | ❌ 进都进不去 | **必须搬**（还得靠 WOL 叫醒） |
| 要过去打游戏 / 看视频 / 陪着 | ✅ 只有那台有显卡和屏幕 | ❌ 遥控给不了本地显卡与输入 | **必须搬**（但这是人主动要的） |

三种都成立 —— 说明 M2 定时搬家**不是冗余**。但注意：只有第一种适合"定时"，
后两种本质上是**人临时决定的**，不该由一条固定时刻的策略替你决定。

### 四、`morning-home` 的判决：留着，但重新说它为什么存在

| 选项 | 好处 | 代价 |
|---|---|---|
| **A. 改成「不搬、只关机」** | 省掉每天一次 2–4 分钟静默；不产生新快照 | ①要新代码：一张"自己关自己"的票 + 「鱼不在这台机器上才允许关」的闸；②**鱼在 Windows 时这条策略只能空转**（关了就等于杀鱼），一半情况下没作用；③白天想用它打游戏得先 WOL（约 23 秒）；④"回巢"这个动作没了，NAS 上的本体只能靠别的时机回去 |
| **B. 留着（现有：回巢 + 关机）** | 已经真机验过的链路（回执 → 键鼠闸 → 关机票 → 先死后生）；白天 Windows 真的关着不烧电；鱼回到常开的 NAS | ①每天一次 2–4 分钟静默（现在有 E1「走了/还在路上」垫着，但断线仍然是真的）；②每天约 30 MB 快照搬家；③09:00 之后想打游戏得手动搬回来，或提前 `/molt stop-auto` |

**我推荐 B：留着，但把它重新表述成「回巢 + 释放桌面」，而不是「让鱼可达」。**

理由是遥控优先恰好**削弱了搬家的必要性**，却没有削弱"本体该住在常开机器上"这件事：
白天把本体留在 NAS（低功耗、7×24），把桌面关机（噪声、电费、别让它当服务器），
这是资源调度，不是可达性。也就是说：遥控优先成立之后，`morning-home` 的价值从
"让你在别处能找到它"变成"**让那台贵机器可以休息**"—— 目标变了，动作没变。

## D18 · 鱼待在 NAS 上怎么控制另一台的 DSH（已实现，2026-11-18）

主人 m22697：*"现在 DSH 只监听 127.0.0.1:3082，我在 NAS 上够不着，必须自己搬回 Windows
才能指挥它。给一条能跨机连过去的路，让我待在 NAS 也能发 prompt 和读 history。"*

### 为什么不能"直接连过去"

不是防火墙，也不是端口没开。DSH 的 host 服务**按回环地址做 Host 校验**（`dsh_connector`
的 README 也这么写：http 模式要求 `http_base_url` 是回环地址，其它 authority 会被拒）。
从 NAS 发 `POST http://192.168.50.63:3082/api/session/list` 会被对端按"你不是本机"拒掉，
表现为一句很难看懂的 4xx —— 这比"连不上"更难排查。

### 选的做法：**由账本代转**

```
鱼在 NAS ──HTTP──> warden(6186) /dsh ──HTTP──> Windows:3082/api/<method>
                                            Host: 127.0.0.1:3082   ← 改写这一行
```

选它而不是改绑地址或加白名单，理由三条：

1. **不用动 DSH**。它是第三方的、我们不发版的东西；改它的监听地址等于给自己造一个
   "上游升级就失效"的补丁。
2. **只有一台机器需要出网**。NAS 本来就要同时看见两台（心跳、账本、代转都是它），
   而 Windows 不需要知道"有人在外面"。
3. **范围天然可收窄**。代转口是**三个方法的白名单**（`session/list`、`session/events`、
   `session/prompt`），不是一条任意转发的隧道。

### 三条硬约束

| 约束 | 代码在哪 | 为什么 |
|---|---|---|
| 只允许三个方法 | `molt/dshrelay.py::ALLOWED_METHODS`，且在**发请求之前**判 | 代转 = 在另一台机器上执行一次 RPC，多放一个就是多一个入口 |
| 目标必须有账本地址 | `dshrelay.resolve_base()`，取不到直接报错 | 绝不退回 `127.0.0.1`：那会让 NAS 连自己，把配置问题伪装成网络问题 |
| 不重试、不缓存、不解释 | `dshrelay.call()` 只做一次 | 代转层一旦"帮你重试一次"，调用方就分不清自己看到的是一次还是两次 |

### 用法

```bash
molt dsh sessions --shell desktop-h2kgiao              # 那台机器上有哪些会话
molt dsh history  --shell desktop-h2kgiao --session <id> --limit 20
molt dsh send     --shell desktop-h2kgiao --session <id> "在吗" --dry-run
molt dsh send     --shell desktop-h2kgiao --session <id> "在吗"       # 真的发
molt dsh call     --shell desktop-h2kgiao --method session/list --args '{"_request":{}}'
```

`send` 默认 `mode="queue"`（排在这一轮之后），`--steer` 才是"插进去改方向"——

## D19 · "300 秒没人碰键鼠才关"要不要放宽（等主人拍板，2026-11-18）

现状：`POWER_MIN_IDLE_SECONDS = 300.0`。鱼搬走 / 鱼已经在家之后要给旧壳投关机票，
但如果**最近 5 分钟里有人动过键鼠**，它就只记一条 `skipped`，不关。

这条闸是 E3 加的，当时理由是：关机的代价不对称 —— 该关没关只是多烧一晚电，
不该关却关了是人正在用的机器黑掉。但现在它和你说的"9 点就关"直接冲突：
**你 9 点要是正坐在这台电脑前，它不会关，只会在账本里写一句"刚才有人动过"。**

### 三个选项（我给推荐，你拍）

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 把闸从 300 秒放到 **60 秒**，并允许按策略配 `power_min_idle_seconds` | 你在 9 点前 1 分钟内动过鼠标，它仍然不关 —— 但正常坐着的间隔很难短于 60 秒 |
| B | 把闸设成 0（无条件关） | 9:00 你真在用电脑，它也会关。这是"我说了要关，就一定要关"的语义 |
| C | 保持 300 秒，改成"有人在用就发一条提醒，不关" | 最安全，但等于你这台机器每天早上都要人回一句 |

**我的倾向是 A**，理由：这道闸不是为了"保护你可能在用"，而是为了不赌 ——
而 5 分钟太长了，长到它和"说好的 9 点"已经不是同一件事。60 秒仍然拦得住
"人正在敲键盘"的情形，同时又让"9 点整"在绝大多数日子里成立。

选 B 的话我会在文档里明确写清：**这条策略的语义是"到点就关，不看你正在干什么"**，
并且把 `/molt keep` 这条出口的存在写进播报之外的地方（否则你只有 120 秒窗口能救）。

### 照着敲的版本

这一节是判定与回滚的依据；**给主人的一页纸**（含"怎么确认自己是管理员 / 怎么开管理员终端"）
在 `docs/ADMIN-D20.md`。

### A · 防火墙阻止 3082 的入站（推荐）

**前置**：管理员 PowerShell。**为什么推荐**：Windows 防火墙不过滤回环流量，所以
`127.0.0.1:3082` 照旧可用 —— 代转链路（6191 → 回环 3082）不受影响，而局域网被切断。

```powershell
# 执行（只有这一条）
New-NetFirewallRule -DisplayName "molt: block DSH 3082 from LAN" `
  -Direction Inbound -Protocol TCP -LocalPort 3082 -Action Block -Profile Any
```

| 判据 | 怎么验 | 通过时应该看到 |
|---|---|---|
| 成功①局域网被切 | 在 **NAS** 上：`curl --max-time 4 -sS http://192.168.50.63:3082/api/session/list -d '{}'` | **超时 / 连接被拒**（不是 200） |
| 成功②本机照旧 | 在 **Windows** 上：`curl -s http://127.0.0.1:3082/api/session/list -d '{}'` | **200**，能返 JSON |
| 成功③代转照旧 | 在 **NAS** 上：`molt dsh sessions --shell desktop-h2kgiao` | 正常列出 184 个会话 |
| 失败①（规则没生效） | 同成功① | 仍返回 200 → 规则没匹配上（检查 profile 是否 Any、端口是否 3082） |
| 失败②（回环被误伤） | 同成功② | 本机也连不上 → 说明拦到了回环（少见，但要立刻回滚） |

**回滚**（一条）：

```powershell
Remove-NetFirewallRule -DisplayName "molt: block DSH 3082 from LAN"
```

验证回滚：NAS 上那条 `curl` 又能 200（说明回到现状）。

**副作用 / 限制**：只挡入站 TCP；不影响本机任何进程。若将来 DSH 换了端口，这条规则失效但也不会有害。

### B · 只允许 NAS（`192.168.50.50`）访问 3082

**前置**：管理员；NAS 已有 DHCP 保留（`192.168.50.50`）。

```powershell
New-NetFirewallRule -DisplayName "molt: allow DSH 3082 from NAS only" `
  -Direction Inbound -Protocol TCP -LocalPort 3082 -RemoteAddress 192.168.50.50 -Action Allow -Profile Any
New-NetFirewallRule -DisplayName "molt: block DSH 3082 from others" `
  -Direction Inbound -Protocol TCP -LocalPort 3082 -Action Block -Profile Any
```

| 判据 | 怎么验 | 通过时应该看到 |
|---|---|---|
| 成功①NAS 仍能直连 | NAS 上 `curl http://192.168.50.63:3082/api/session/list -d '{}'` | **200**（这是 B 与 A 的关键区别） |
| 成功②别的机器被挡 | 任意第三台设备（手机/笔记本）打同一地址 | 超时 / 拒绝 |
| 成功③本机照旧 | Windows `127.0.0.1:3082` | 200 |
| 失败①NAS 也被挡 | 第一条规则 | NAS 超时 → 多半是 `RemoteAddress` 写错或 DHCP 换了 IP |
| 失败②顺序写反 | 先 Block 后 Allow（Windows 防火墙 Block 优先） | NAS 也被挡 → 两条规则**顺序无所谓**，但 Allow 必须先存在；确认 `Get-NetFirewallRule` 里两条都在 |

**回滚**：

```powershell

Remove-NetFirewallRule -DisplayName "molt: block DSH 3082 from others"
```

**副作用**：NAS 仍然直连 3082（少一层代转，但暴露面比现状小）；换机器/改 IP 时要同步改。
